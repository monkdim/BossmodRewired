# Contributing to BossMod Rewired

Thanks for considering it. This is a small fork with one maintainer, so the rules below are mostly about
what can realistically be reviewed and trusted rather than about taste.

Read this before opening a pull request, and say in the description that you have.

## No AI-generated contributions

Do not open a pull request containing code that was generated by an AI tool or written with heavy AI
assistance. No exceptions.

This is not a position on the tools. It is about what a pull request costs to accept. Reviewing a change
here means deciding whether it behaves correctly in a real duty, and there is no test suite that can answer
that. What makes a change trustworthy is that somebody understood it and watched it work. Generated code
arrives fluent, plausible, and frequently untested, and separating the ones that were understood from the
ones that were merely produced takes longer than writing the change would have.

If you have used a tool to help you understand the codebase, that is your business. What lands in a pull
request should be code you wrote, can explain line by line, and have run.

## Test encounter modules in an actual duty

Replaying a recording is not enough. A module has to be watched working in the fight it is for, because
timing, targeting, and what the module can actually see at the moment it needs to see it are exactly the
things a replay flatters.

Say in the pull request which fight you tested it in, and how many pulls.

## Keep general-purpose code out of encounter modules

New methods and helpers belong in the shared sections where anything can use them. A useful function
buried in one boss module is a function the next person writes again.

## Do not refactor shared code without testing it broadly

Everything outside an encounter module is used by every module and is expected to behave a particular way.
Changing it can break fights you never opened. If a refactor is genuinely needed, say what you tested and
what you did not.

## Build clean, and match the code around you

Building the solution after your change should add no new errors, warnings, or messages. Match the style of
the file you are editing rather than the style you prefer. No sweeping formatting changes.

## Especially welcome

- **Encounter modules for content that has none.** Older and lower-level content is the largest gap, and it
  is also the content this fork's analysis has the least data about.
- **Fixes to modules for fights you actually run.** Somebody who does the fight weekly will catch things no
  amount of reading finds.
- **Recordings.** Not code at all, and often more useful than code. This fork derives positions from real
  fights, so a night of pulls from a fight nobody has captured is a genuine contribution. The plugin can
  share them for you, with names stripped, if you turn that on during setup.

## A note on upstream

Encounter modules here are largely the work of
[BossMod Reborn](https://github.com/FFXIV-CombatReborn/BossmodReborn) and
[awgil's ffxiv_bossmod](https://github.com/awgil/ffxiv_bossmod). If you have found a bug in one, it very
likely exists upstream too, and reporting it there gets it fixed for everybody rather than only for this
fork's users.

This fork pulls upstream changes in periodically. It does not send changes back automatically, so a fix you
want upstream to have is one you should take to them yourself.
